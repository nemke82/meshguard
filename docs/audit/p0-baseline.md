## 3. Architecture as found

```
ui/src/main.js  ──invoke/listen──▶  src-tauri commands.rs ──▶ AppState (in-memory)
                                         │
                                         ▼
                                   mesh_radio.rs (meshtastic StreamApi)
                                         │
                 desktop: btleplug/bluer │ Android: Rust thread polls Kotlin
                                         ▼
                           BlePlugin.kt (generated by scripts/patch-android.sh)
```

### BLE ownership on Android

- `BlePlugin` is a Tauri `Plugin(activity)` and uses the **Activity** as its context for `BluetoothManager`, `connectGatt` and notifications.
- I/O is a Rust `std::thread` loop (`mesh_radio.rs::build_android_ble_stream`) that calls `run_mobile_plugin("readFromRadio")` every 75 ms when idle, and `writeToRadio` for outgoing data. Each call goes through the Tauri `PluginHandle`.
- No FROMNUM notification subscription: reads are pure polling, which costs battery and adds latency.
- **Consequence:** receiving, decrypting and notifying all depend on the Tauri runtime and the plugin instance bound to the Activity. Nothing keeps the process alive when the Activity is gone. There is no `Service`, no `FOREGROUND_SERVICE*` permission and no `foregroundServiceType` in the patched manifest.

### Notification pipeline

- `mesh_radio.rs::handle_incoming_packet` → `show_android_notification` → Kotlin `showNotification` builds a plain `Notification.Builder` on the `meshguard_messages` channel with a launch intent.
- It has no `MessagingStyle`, `Person`, shortcut or `RemoteInput`, and the notification id is `nodeNum`.
- Lock-screen visibility is `VISIBILITY_PRIVATE`, which is good. The body is the decrypted text.

### State and persistence

- `AppState.session_keys` holds keys in memory only (`HashMap<u32, SessionKey>`), and they are lost on process death. This matches the CLAUDE.md "passphrase never stored" decision, so background receipt after a restart needs ADR-002.
- `meshguard.json` stores the last BLE address and device name, plus peers (`id` = random UUID, `device_name`, `node_num`).
- **Chat history is not persisted at all.** It lives only in `ui/src/main.js` memory. `localStorage` holds notification settings only.

### Protocol and crypto

- v1 wire: `nonce(12) | AES-256-GCM([type][UTF-8])`, with no AAD and no message id.
- `protocol.rs::from_wire` assigns a **fresh UUID and the receive time** on every receipt, so duplicates cannot be detected (confirms RFC §1).
- Key derivation: HKDF-SHA256 (salt `meshguard-p2p-v1`) over `SHA-256(sorted names | passphrase)`. It depends on mutable device long names, and HKDF does not slow offline passphrase guessing.
- Peers are keyed by Meshtastic `node_num`, both in `session_keys` and in `pending_pair_requests`.
- **Reflection:** v1 keys are symmetric and frames carry no direction. A frame Alice sent can be replayed to Alice and will decrypt as if Bob sent it. v2 fixes this with direction-bound AAD (ADR-003).

### Payload budget

- The comments and tests assume a limit of 228 bytes (and "~200" in places).
- The protobufs in `meshtastic` 0.1.8 define `Constants::DATA_PAYLOAD_LEN = 233`, which explicitly *excludes* the `Data` protobuf's own field overhead.
- The real usable `PrivateApp` payload on T1000-E firmware still needs measuring (P3). Until then v2 keeps 228 as a conservative, configurable default.

## 4. Findings fixed in this PR

| # | Finding | Fix |
|---|---|---|
| F1 | `mesh_radio.rs` logged the first 40 characters of every decrypted message at `info` level (RFC §5.4 violation) | Logs byte length and local id only |
| F2 | `BlePlugin.kt` (via `patch-android.sh`) logged the notification **body**, i.e. decrypted text, to logcat | Logs title and node number only |
| F3 | Crypto and the v1 codec existed only inside the Tauri crate, so a native Android service could not reuse them | Moved unchanged to `crates/meshguard-core`. The `src-tauri` modules re-export or delegate to it, and the existing tests still pass. |
